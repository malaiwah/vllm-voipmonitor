Thanks for driving this unification — one scoping question and one interface
request, raised now because both are cheap to accommodate while the lifecycle
is being defined and expensive after.

The RFC scopes out operations that "do not replace the base checkpoint" (LoRA
add/remove, EPLB expert rebalance, sleep/wake, KV-cache operations). That
boundary is clean, and I'd like to confirm which side of it a re-quantization
reload falls on.

**The case:** reloading a layer (or a subset of experts) at a *different
quantization configuration* than it was originally loaded with — same
architecture, same checkpoint lineage, different bits. Unlike the excluded
operations, this genuinely replaces base-checkpoint-derived content, so by the
RFC's own criterion it seems to belong *inside* the unified lifecycle, as a
loading source alongside checkpoint-load and same-config reload.

There is already precedent adjacent to this in-tree: the layerwise reload path
deliberately deletes the `_already_called_process_weights_after_loading` guard
so online quantization re-runs on freshly loaded weights, and RFC #50281 (with
#51285/#51392) is building per-layer online quantization configuration. The
natural composition of those two lines of work is exactly "reload this layer
under a different per-layer quant config" — which today would collide with the
implicit assumption I want to flag:

**Request: the unified session/lifecycle abstraction should not assume that a
reloaded tensor is byte-identical in size and layout to the originally loaded
one.** Today every runtime weight-update path is a same-shape `copy_` into
pre-existing storage (which is also what keeps CUDA-graph references valid —
e.g. the reload path's comment about copying into original tensor storage to
preserve cudagraph refs). That is the right *default*, but if the session API
hard-codes it — for example by validating incoming tensors against resident
`shape`/`nbytes` — then any future source whose quant config differs from the
resident one is excluded at the API layer rather than by an explicit design
decision. A per-source capability flag (default: sizes must match) would keep
today's semantics while leaving the door open.

I'm asking from a concrete direction: workload-driven per-expert precision
selection under tight memory budgets, where a reload legitimately materializes
a different byte count for the same logical tensor. I don't need that case
solved in this RFC — only not foreclosed by it.
